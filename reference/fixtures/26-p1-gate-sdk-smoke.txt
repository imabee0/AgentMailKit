P1 GATE — SDK SMOKE (Python + Node), captured 2026-08-16
========================================================

The plan's P1 gate reads: "Python+Node SDK smoke (create/list/delete across scopes) +
schemathesis over implemented paths; dual-target conformance diff clean for all endpoints
implemented in this phase". This fixture captures the SDK-smoke half of that, both clients.
(The conformance-diff half is fixture 25; schemathesis is not yet run and the ledger says so.)

WHAT IS BEING PROVEN, and why it is not the same thing fixture 25 proves.
Fixture 25's diff shows our responses have the reference API's SHAPE. It says nothing about
whether an official client can USE them: a response can be structurally identical to the
reference's and still break a typed client on deserialization, on a required-field model, or
on the client's own base-URL routing. This runs both official clients, unmodified, against
`amkd --role api` on localhost with nothing changed but the base URL — the entire V1
acceptance criterion — and drives a full create/list/get/update/delete cycle across all three
resources the P1 control plane implements.

WHAT EACH CLIENT COVERS THAT THE OTHER DOES NOT.
  Python `agentmail==0.5.9` — pydantic models. A response missing a required field, or
  carrying one of the wrong type, raises at construction. It is the strict one.
  Node `agentmail@0.5.19` — camelCase mapping over the wire's snake_case, RFC 3339 strings
  coerced to real `Date` objects, and the `am_eu_` prefix routing a key to
  `api.agentmail.eu` [SPEC:sdk environments.ts, Client.ts:80] — the one client behaviour
  that could take a caller off our base URL entirely, which is why the smoke mints a key and
  asserts the prefix rather than trusting the constant.
  What the Node client does NOT do, probed rather than assumed: reject a response missing a
  required field. Every generated resource client parses with
  `skipValidation: true, unrecognizedObjectKeys: "passthrough"`, so a missing field arrives
  as `undefined` and our extra live fields (`organization_id`, `smtp_id`) pass through
  un-mapped. A first draft of this fixture claimed the opposite; the probe below is what
  corrected it, and the claim is recorded here with its evidence so the next reader does not
  have to re-derive it.

  $ node -e '... serialization.pods.Pod.parse(<body missing required `name`>, <client opts>)'
  missing required `name`, client options -> ACCEPTED
    value: {"podId":"p","updatedAt":"...","createdAt":"...","organization_id":"o"}
  bad timestamp -> ACCEPTED, createdAt is [object Date], updatedAt is not-a-timestamp

  The second line is why the Node smoke asserts `instanceof Date` on every timestamp it sees:
  a value the SDK could not parse is passed through as the raw string, so the Date assertion
  is the thing that separates "RFC 3339, three fractional digits, Z" from anything else.

VERSIONS ARE PINNED EXACTLY: `conformance/requirements-gate.txt` (agentmail==0.5.9) and
`conformance/package.json` + `package-lock.json` (agentmail 0.5.19). Both are the versions
P-1 surveyed. A gate that passes against a newer client than the plan read is not this gate.

SECRETS: `amk init` prints the root key once; p1-gate.sh captures it into a shell variable and
prints the line as `<redacted>`. No key value appears in this file. The minted-key checks
assert a prefix predicate and an authentication outcome, never a value.

REPRODUCE: ./scripts/p1-gate.sh   (stands up a throwaway `amk_p1gate` database, migrates,
inits, serves on 127.0.0.1:8111, seeds state parity, runs the conformance diff, then both SDK
smokes; drops the database and stops the server on exit. All three halves must pass.)

--------------------------------------------------------------------------------------------
FALSIFICATION — the Node half proven able to FAIL, and to fail the gate
--------------------------------------------------------------------------------------------
A gate that has only ever passed is not evidence that it can fail; the plan says so about
tests and it is true of gates. Before this fixture was written, one expectation in
sdk_smoke.mjs was inverted in place — `a minted key never begins am_eu_` was flipped from
`false` to `true`, so a correct server must now fail it — and the whole gate re-run. The
poison was reverted immediately afterwards and the file re-verified (`grep -c POISONED` -> 0).

What this pins, and it is three separate things, each of which has silently failed in some
check in this project before: the assertion actually compares (it reported the mismatch with
both sides), the script's exit code follows its failures rather than its last statement, and
p1-gate.sh's three-way conjunction propagates a third-half failure to the gate's own exit.
