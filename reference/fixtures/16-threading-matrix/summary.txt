================= INFERRED RULE SET (confidence: HIGH within tested conditions) =================
R1. Grouping key = RFC Message-ID reference chain. A message joins an existing thread ONLY when it
    carries In-Reply-To and/or References pointing at a Message-ID already in that inbox's thread
    (case a). This was the sole join observed.
R2. Subject is NOT a grouping key. Identical subjects (b, d0/d1), subject-prefix variants
    Re/RE/Fwd/FW/AW/[list] (c), trailing-whitespace, and empty subjects (f) all produced SEPARATE
    threads. Subject-prefix normalization does not exist for threading purposes here.
R3. Correspondent (From) is NOT a grouping key, neither sufficient nor necessary: same-sender
    same-subject messages did not merge (c,d,f); the reply that DID merge (a) happened to share a
    sender, but merging is explained by R1, not the shared sender.
R4. Threads are PER-INBOX. thread objects carry inbox_id; identical mail to a second inbox in the
    same pod got a distinct thread with the other inbox_id (e). Threads never span inboxes.
R5. Ingest normalization side-notes: trailing subject whitespace is stripped in the stored subject;
    an empty subject is stored as an ABSENT "subject" field (not "").

Net: AgentMail inbound threading == strict header-linkage (In-Reply-To/References), scoped per inbox.
It behaves like RFC 5322 References threading, NOT Gmail-style subject+participant threading.

================= DIMENSIONS THIS MATRIX DID NOT COVER (honest gaps) =================
G1. In-Reply-To vs References in ISOLATION — case (a) sent BOTH; not determined which alone suffices,
    nor whether a multi-hop References chain (A<-B<-C) transitively joins.
G2. References pointing at a Message-ID in a DIFFERENT existing thread (thread MERGE behavior).
G3. Reply whose References match but whose subject is unrelated (does header linkage override subject
    mismatch — expected yes under R1, but untested).
G4. AUTHENTICATED mail — every probe message was "unauthenticated" (OVH is in no relevant SPF and
    signs no DKIM). Threading of authenticated mail was not exercised; assumed identical but unverified.
G5. TIME WINDOW — whether identical-Message-ID-chain or same-subject grouping decays after a gap.
    This is case (g), deliberately deferred (see g-window-bisect.sh). Closure horizon T+30d, non-blocking.
G6. Malformed/duplicate Message-IDs, missing Message-ID (server-generated), and cross-pod grouping.
G7. n=1 per cell (no repeat trials); results are deterministic-looking but not statistically repeated.
