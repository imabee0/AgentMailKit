{"organization_id":"133c9cbe-…","api_key_id":"e24f8809-ccc8-4142-97d6-ebb313abd3d1","prefix":"am_us_ae0c53","name":"amk-probe-key","created_at":"2026-08-16T03:56:42.259Z","api_key":"<redacted>"}

GET /v0/api-keys/e24f8809-… -> 404
{"name":"NotFoundError","code":"not_found","message":"Route not found","fix":"No route matches this path and HTTP method. …"}

OBSERVED:
- **DELETE is 204**, not the 200 `openapi.json` documents. That makes the spec **0 for 3** on DELETE
  status codes: pods 204, inboxes 202, api-keys 204, all documented as 200. Treat every remaining
  documented DELETE status as unverified.
- **There is no GET-by-id route for api-keys.** The 404 body says *"Route not found"*, not a
  resource-not-found — it is the fallback, so the route does not exist. Consistent with the
  enumeration: the spec has `GET /v0/api-keys` (list) and `DELETE /v0/api-keys/{api_key_id}`, and no
  GET by id. `amk_store::api_keys::get` therefore has **no wire route** in the first amk-http
  dispatch; it exists for `authenticate` and for internal use. Do not add a route for it.

================================================================================
THE MINTED KEY SHAPE — AND IT CONTRADICTS WHAT WE BUILT
================================================================================

From the create response above, with the secret redacted but its structure preserved:

  prefix     "am_us_ae0c53"                    = `am_us_` + **6** lowercase-hex characters
  api_key    "am_us_" + 64 lowercase-hex chars = the prefix's 6 hex, then 58 more

So the visible `prefix` is the first 6 characters of a 64-character lowercase-hex secret.

**What `crates/amk-store/src/api_keys.rs` mints today does not match:** `SECRET_LEN = 32` and
`VISIBLE_LEN = 8`, over a URL-safe alphabet rather than hex. Both constants were tagged `[ASSUMED]`
by the api-keys contract, correctly and explicitly, because the only prior evidence was
`reference/fixtures/05-error-catalog.http`'s `am_us_00000000000000000000000000000000` — a *rejected*
key, whose length told us only what the gateway would accept as well-formed, not what it mints.

That assumption is now superseded by an observation, and `prefix` is a **wire field returned in
every `ApiKey` response**, not an internal detail — so it is pinned, not ours to choose. The
correction (`SECRET_LEN` 64, `VISIBLE_LEN` 6, lowercase hex) belongs in `amk-store`. Note the
security direction is favourable: the observed secret is *longer* than ours (64 hex ≈ 256 bits
versus 32 URL-safe chars ≈ 190), so matching it does not weaken anything.

The `am_us_` tag itself is confirmed a second time, and a minted key still never begins `am_eu_`.
